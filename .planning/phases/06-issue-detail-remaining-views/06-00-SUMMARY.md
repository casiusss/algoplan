## Decisions Made

- **Catalog version drift accepted for `@zxcvbn-ts/language-en`** — registry has no 3.0.4 release for that single package; pinning at `^3.0.2` preserves v3.x major-compatibility across all three. The catalog comment documents this.
- **`useNavigationFlash` placed in `packages/core/navigation` despite browser-only deps** — sonner imports require the browser DOM, but the hook needs to live alongside `useNavigationStore` for downstream import ergonomics. Mitigation: every sessionStorage call is gated with `typeof window !== "undefined"` so SSR is safe. JSDoc explicitly documents the relaxation.
- **Module-scope (not per-mount) lazy import cache** — multiple meter mounts (signup page + reset-password page open concurrently in dev) share a single zxcvbn promise, so the dictionaries are downloaded and parsed exactly once across the entire app session.
- **`dragstrip-coverage` walks every DragStrip occurrence per file** — earlier draft only checked the first occurrence, which would have given a false PASS on multi-column step files. The current iteration finds the immediate JSX parent of each `<DragStrip` and asserts both flex class + first-child position.
- **`step-first-issue.tsx` excluded from the enumeration** — it's not a full-window page, it's a step rendered INSIDE `onboarding-flow.tsx`'s already-DragStrip'd container. Documented in the test file header.

**3. [Rule 3 — Blocking] Initial dragstrip-coverage regex matched the wrong flex container in multi-section files**

- **Found during:** Task 3 (first run of `dragstrip-coverage.test.ts`)
- **Issue:** The first iteration of the test used `src.match(flexOpenRegex)` which returns the FIRST match in the file. For `invite/invite-page.tsx`, `step-welcome.tsx`, and `step-workspace.tsx`, the first flex element appears in an early-return branch (loading state, illustration column) far above the actual page-root flex container — leading to false negatives.
- **Fix:** Rewrote the test to find every `<DragStrip` occurrence, then walk backward to locate the immediately-enclosing JSX open-tag for EACH one. Asserts that parent has `flex` in className AND nothing JSX exists between the parent open-tag and the DragStrip. This is the correct structural property (DragStrip is the first child of its OWN flex column, not the file's first flex element).
- **Files modified:** `packages/views/__tests__/dragstrip-coverage.test.ts`
- **Verification:** All 24 assertions GREEN (12 files × 2 properties: contains-DragStrip + first-child-of-flex-parent). Multi-column step files validated for both columns.
- **Committed in:** `9e22f4ce` (Task 3 commit)

**4. [Rule 1 — Bug] Plan's draft `password-strength-meter.test.tsx` had a flawed memoization assertion**

- **Found during:** Task 2 (first run of meter tests)
- **Issue:** The plan-suggested test design counted `vi.mock` factory invocations to assert "no second import after first". But Vitest's mock factory body runs exactly ONCE per test file (during the first lazy import) — and `vi.resetModules()` does NOT reset that bookkeeping. So after the first test triggered the factory, all subsequent tests' counters showed 0 and the memoization assertion failed even though behavior was correct.
- **Fix:** Introduced a SECOND counter `zxcvbnCalls.count` (incremented by the mocked `zxcvbn` function itself) which is reset per-test via `beforeEach`. Memoization tests now assert "calling zxcvbn once for password A and re-rendering with the same A doesn't call it again" — direct behavioral assertion. Kept `importFactoryCalls` for the file-lifetime "import factory fires exactly once" sanity check.
- **Files modified:** `packages/views/auth/password-strength-meter.test.tsx`
- **Verification:** All 9 meter assertions GREEN; `importFactoryCalls.count === 1` confirms the lazy import factory fires exactly once across the entire test file.
- **Committed in:** `9cb5fa45` (Task 2 commit)

## Lazy-Load Gate Strategy (UI-CHECK FLAG-5.1 Resolution)

The strict assertion "PasswordStrengthMeter does NOT load @zxcvbn-ts/core at module load — only after first non-empty render" is satisfied by:

1. The meter source uses a module-scope `let zxcvbnPromise: Promise<...> | null = null` with a `loadZxcvbn()` accessor that creates the promise lazily — there is NO top-level `import "@zxcvbn-ts/core"` in the meter file.
2. The test file mocks `@zxcvbn-ts/core` with a `vi.mock` factory that bumps a hoisted `importFactoryCalls.count` counter when the mocked module is first dynamically imported. By the end of the suite this counter MUST equal 1 — proof that the import fired exactly once across the file's lifetime.
3. A dedicated test asserts `importing the meter module + rendering with empty password` results in `zxcvbnCalls.count === 0` (no scoring call, hence no lazy import resolution).
4. A second dedicated test asserts that after the first non-empty render and one debounce tick, `zxcvbnCalls.count >= 1`.

Together, (1) is the static guarantee, (2) is the file-lifetime "fires exactly once" guarantee, (3) is the empty-render guarantee, and (4) is the non-empty-render guarantee.
