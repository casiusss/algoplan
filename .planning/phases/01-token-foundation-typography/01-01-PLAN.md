<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CSS file → bundler → browser | Tailwind v4 reads tokens.css at build time; values become CSS custom properties served to client browsers |
| Token override (`.dark`) → cascade | Class-based dark mode means any code with permission to add `dark` class to `<html>` can flip the entire palette |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01-01 | Tampering | tokens.css → CSS bundle | accept | CSS files are code, protected by repo write controls. PR review catches malicious palette swaps. |
| T-01-01-02 | Information Disclosure | OKLCH color values | accept | Brand colors are public information (visible in any rendered page). No information disclosed via the file. |
| T-01-01-03 | Denial of Service | Malformed `oklch()` | mitigate | `pnpm typecheck` + dev server boot catch CSS parse errors before merge. Chrome falls back to inherited color on invalid `oklch()` per CSS Color Module Level 4 spec. |
| T-01-01-04 | Elevation of Privilege | `.dark` class injection | accept | Only authenticated client-side JS can add `dark` to `<html>`. Theme is a UI preference, not a security boundary. |
</threat_model>
