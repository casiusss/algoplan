# Phase 5 — UI Design Contract

> Visual and interaction contract for the AlgoPlan Issues page — restyled List view, redesigned Kanban Board view, persistent List/Board view toggle, inline column task-add, and full migration from `@dnd-kit/core` (v6) to `@dnd-kit/react` (v0.4.0). Generated by gsd-ui-researcher; verified by gsd-ui-checker. Tokens (Phase 1), atoms (Phase 2), and the AppTopbar slot system (Phase 4) are inherited; this contract reuses them and introduces zero new tokens.
>
> **Scope shape note.** Phase 5 touches three layered surfaces:
>
> 1. **DnD plumbing** — replace `@dnd-kit/core` + `@dnd-kit/sortable` + `@dnd-kit/utilities` (v6/v10/v3) with the unified `@dnd-kit/react` v0.4.0 API (`DragDropProvider`, `useDraggable`, `useDroppable`, `useSortable` from `@dnd-kit/react/sortable`, `AutoScroller` from `@dnd-kit/dom`). Cross-column moves now use the built-in `group` pattern. The `onMoveIssue(issueId, newStatus, newPosition?)` signature stays unchanged so existing tests remain valid (KBN-06).
> 2. **Visual restyle** — both `BoardView` (cards, columns, drag overlay) and `ListView` (rows, accordion headers, sticky footer) consume Phase 1 tokens, Phase 2 atoms (`AccentBar`, `TagChip`, `AvatarInitial`, `SegmentedControl`), and the new Italic Inter axis (Phase 1 D-12) for column headers (KBN-02, KBN-05, KBN-07).
> 3. **Interaction additions** — inline `+ Task hinzufügen` row per board column (KBN-03), persistent List/Board toggle in `IssuesHeader` swapped from current dropdown to `SegmentedControl` (KBN-04), and a corrected scroll-collision strategy that does not drift drop targets in scrolled columns (KBN-02).

## Typography

This phase uses ONE new typography role: **Column heading** in Inter Italic. All other roles inherit from Phases 2 + 4.

| Role | Tailwind class | Computed | Weight | Line height | Used by |
|------|---------------|----------|--------|-------------|---------|
| Column heading (italic) | `text-sm italic` | 14px | `font-semibold` (600) | `leading-tight` (1.25) | `<BoardColumn>` header label (e.g. `"In Progress"`); `<ListView>` accordion header status label |
| Body / row content | `text-sm` | 14px | `font-medium` (500) | `leading-snug` (1.375) | List row title; card title |
| Caption | `text-xs` | 12px | `font-medium` (500) | default | Card identifier (`MUL-123`); column count badge; due-date pill |
| Numeric badge | `text-xs` | 12px | `font-semibold` (600) | `leading-none` | Total count next to column header; sub-issue progress count (`3/5`) |
| Inline-add input | `text-sm` | 14px | `font-normal` (400) | `leading-snug` | The `<input>` in the per-column inline-add row — slightly lighter weight than card title to read as "in flight" |

**Italic usage:** Column headers ARE the only italic surface in Phase 5. Per Phase 1 D-12 italic is reserved for display-level brand identity; board column headers are the product's headline UI element. Card titles, list row titles, dropdowns, buttons, and chips remain UPRIGHT.

**Numerals:** Use `tabular-nums` on every numeric badge (column count, sub-issue progress count, due-date pill that includes day numbers). Prevents jitter as counts change during drag.

**Font-family token:** `--font-sans` only. The phase never references `--font-serif` or `--font-mono`.

## Color

The phase consumes Phase 1 semantic tokens exclusively. Status colors flow through `STATUS_CONFIG` (existing in `packages/core/issues/config/status.ts`); priority colors flow through `PRIORITY_CONFIG`. **No `STATUS_CONFIG` value is changed** in Phase 5 — the existing `bg-warning/5`, `bg-success/5`, `bg-info/5`, `bg-destructive/5` column-tints are correct AlgoPlan tokens and stay in place.

| Role | Token | Usage in Phase 5 |
|------|-------|------------------|
| Dominant (60%) | `--background` (page canvas behind board), `--card` (card surface), `--sidebar` (NOT consumed by board itself; sidebar is Phase 4 chrome) | Cards always `bg-card`; board canvas is `bg-background` (inherits from `SidebarInset`); the column wrapper paints a tinted variant of the status's semantic color (existing `STATUS_CONFIG.columnBg`) |
| Secondary (30%) | `--muted` (column wrapper for backlog/todo/cancelled), `--muted-foreground` (caption text, identifier), `--border` (card border, accordion separator) | Column wrappers consume `bg-muted/40` for neutral statuses; row hover state `bg-accent/50` |
| Accent (10%) | `--brand`, `--tag-p0..p3`, `--warning`, `--success`, `--info`, `--destructive` | Status badge backgrounds (existing); priority chip backgrounds (existing); active drop-target ring (`ring-2 ring-brand`); active List/Board toggle pill (`bg-background` over `bg-muted` track per Phase 2 SegmentedControl); AccentBar leading-edge on cards and list rows (NEW for Phase 5 — see Card / List View sections) |
| Destructive | `--destructive` (== `--tag-p0`) | Overdue due-date text (existing); "Failed to move issue" toast (existing); blocked status badge (existing) |
| Focus ring | `--ring` | All interactive elements: `focus-visible:ring-[3px] focus-visible:ring-ring/50` |

**Accent reserved for** (exhaustive — accent MUST NOT appear elsewhere on board/list views):

1. **Card AccentBar** — `<AccentBar color={priorityToAccentColor(issue.priority)} segments={1} />` painted as the top edge of each card (4px tall, full card width, `rounded-t-lg` to match card corners). Maps `urgent → tag-p0`, `high → tag-p1`, `medium → tag-p2`, `low → tag-p3`, `none → muted`. (NEW for Phase 5 — replaces the current visual where priority shows only inside the card body.)
2. **List row AccentBar (vertical)** — `<AccentBar color={...} orientation="vertical" />` as a 4px-wide leading edge on each list row. Same color mapping as cards. (NEW for Phase 5.)
3. **Active drop target highlight** — when `isDropTarget` is true (from `useDroppable`), the column body adds `ring-2 ring-brand ring-offset-2 ring-offset-background` AND `bg-accent/40`. The brand-green ring is the ONE place dnd-kit interaction state surfaces accent green on the board.
4. **Active List/Board toggle item** — `<SegmentedControl>` from Phase 2 atom inheriting its active treatment (`bg-background` lift over `bg-muted` track, `shadow-sm`). The active pill is the only accent in `IssuesHeader` for the toggle.
5. **Status badges in column headers and list accordion headers** — existing per `STATUS_CONFIG.badgeBg / badgeText` mapping (e.g. `bg-warning text-white` for in_progress). Unchanged.
6. **Priority badges on card** — existing per `PRIORITY_CONFIG.badgeBg / badgeText` mapping (e.g. `bg-destructive text-white` for urgent). Unchanged.
7. **Inline-add submit button** — `<Button variant="default" size="sm">` (primary brand-green) reading `"Hinzufügen"`. The "Abbrechen" button is `variant="ghost"`.
8. **Subscriber dot / draft dot** (existing convention in cards) — unchanged; these decorative dots already use `bg-brand` per Phase 4.

**No hex / no RGB.** Same Phase 1 contract.

**60/30/10 verification:** Cards (~60% — `bg-card`), column wrappers + sidebar tint (~30%), AccentBars + status/priority badges + drop-target ring (~10%) on a typical board screen. The AccentBar is decorative — its visual weight is intentionally light (4px tall) so it does not dominate the 10% accent budget.

**Dark mode:** The Phase 1 tokens already include dark variants for every color used. Phase 5 introduces ZERO `dark:*` overrides. Cards in dark mode = `bg-card` = dark slate tint per `tokens.css`. AccentBars darken to the dark `tag-p*` variants automatically.

## Layout & Composition

The Issues page composition stays exactly as Phase 4 left it. Phase 5 changes only the BODY of the `IssuesPage` content area; the surrounding shell (Phase 4 DashboardShell + AppTopbar) is untouched.

```
┌──────────────────────────────────────────────────────────────────────┐
│  AppTopbar (Phase 4 — searchSlot, FilterChipRow, PrimaryCTA)         │  ← chrome
├──────────────────────────────────────────────────────────────────────┤
│  PageHeader (workspace breadcrumb + "Issues")                        │  ← page-level chrome
├──────────────────────────────────────────────────────────────────────┤
│  IssuesHeader (scope tabs, filter dropdown, display popover,         │  ← page-level toolbar
│                <ViewToggle> NEW)                                     │
├──────────────────────────────────────────────────────────────────────┤
│  Content area — viewMode === "board" → BoardView                     │
│                  viewMode === "list"  → ListView                     │  ← Phase 5 surface
│                                                                      │
│   (BoardView: horizontal-scroll columns, italic headers,             │
│    AccentBar cards, inline-add row per column,                       │
│    drag-and-drop with brand-green drop-target ring)                  │
│                                                                      │
│   (ListView: vertical-scroll accordion, sticky h-12 italic headers,  │
│    AccentBar leading-edge rows, inline-add row per status)           │
├──────────────────────────────────────────────────────────────────────┤
│  BatchActionToolbar (list view only — existing, unchanged)           │
└──────────────────────────────────────────────────────────────────────┘
```

**Important:** the `<ViewToggle>` slot in `IssuesHeader` is the ONLY place the toggle lives. Phase 4's `AppTopbar.searchSlot` is not used for the view toggle — search and view-mode are different concerns. The toggle's home is the page-level toolbar (`IssuesHeader`) because view mode is page-specific (each page may have its own view modes; e.g. inbox doesn't have board/list).

**Switching views must NOT remount.** `IssuesPage` keeps both `<BoardView>` and `<ListView>` as conditional renders (`viewMode === "board" ? <BoardView /> : <ListView />`). React reconciles these as siblings with different keys — they remount. To meet KBN-04's "no full re-mount" criterion **applied to the page chrome** (PageHeader, IssuesHeader, BatchActionToolbar, the `ViewStoreProvider`), the page structure already keeps the chrome stable: only the `<BoardView>` / `<ListView>` subtree swaps. Both views internally consume `useViewStore` for sortBy/sortDirection/cardProperties so switching back restores state instantly. The "no full re-mount" assertion in tests targets these chrome elements remaining mounted across the toggle (verified via `data-testid="issues-header"` reference equality before/after toggle).

### `<DragDropProvider>` wiring (board-view.tsx)

```typescript

import {useSortable, isSortable} from "@dnd-kit/react/sortable";
import {AutoScroller} from "@dnd-kit/dom";

// Inside <BoardView>:
<DragDropProvider
  plugins={(defaults) => [
    ...defaults,
    AutoScroller.configure({
      acceleration: 15,
      threshold: { x: 0, y: 0.3 },
    }),
  ]}
  onDragStart={({source}) => {
    snapshotRef.current = structuredClone(columnsRef.current);
    isDraggingRef.current = true;
    setActiveIssue(issueMapRef.current.get(source.id as string) ?? null);
  }}
  onDragOver={({source, target}) => {
    // v0.4 fires onDragOver for cross-group hover; the source's
    // `group` / `index` are auto-tracked by useSortable. We DON'T
    // mutate columns state here — that happens in onDragEnd.
    // (Visual feedback via isDropTarget on the column.)
  }}
  onDragEnd={({source, canceled}) => {
    isDraggingRef.current = false;
    setActiveIssue(null);

    if (canceled) return;
    if (!isSortable(source)) return;

    const {initialIndex, index, initialGroup, group} = source;
    if (initialGroup == null || group == null) return;

    // Compute final position from neighbor positions in the new column
    const finalCol = group as IssueStatus;
    const finalIds = currentColumnIdsForGroup(group);
    const newPosition = computePosition(finalIds, source.id as string, issueMapRef.current);

    onMoveIssue(source.id as string, finalCol, newPosition);
  }}
>
  {/* columns map */}
</DragDropProvider>
```

### Auto-scroll plugin (KBN-02 fix)

The `AutoScroller` plugin from `@dnd-kit/dom` replaces v6's manual scroll-collision logic. Configured with `threshold: { x: 0, y: 0.3 }` (only vertical scroll triggers; horizontal scroll requires explicit pointer at the edge — prevents the board from scrolling sideways while the user drags vertically within a column).

The plugin auto-detects the SCROLLABLE ANCESTOR of each droppable (column body's `overflow-y-auto` div) and re-measures collision rectangles relative to the scroll position EVERY FRAME. This eliminates the v6 "drop target drifts when column is scrolled" bug (KBN-02).

### Race immunity (KBN-01)

The KBN-01 success criterion is: "Dragging a card between Kanban columns updates the issue status — the card settles in the new column without flickering back (WS event from a second browser tab does not interrupt the drop)."

The mechanism, end-to-end:

1. **Snapshot on drag start.** `snapshotRef.current = structuredClone(columnsRef.current)`. v0.4's drag-end can reset to this snapshot if `event.canceled === true` (e.g. Esc pressed mid-drag).
2. **No optimistic columns mutation during drag.** Unlike v6 where we mutated the local columns state on `onDragOver`, v0.4 owns the visual reorder via `useSortable`'s built-in `index` / `group` tracking. We do NOT call `setColumns` during drag. (Removes one source of WS-event/local-state races.)
3. **`onMoveIssue` fires once at drag end.** Calls `useUpdateIssue().mutate({ id, status, position })` which:
   a. `qc.cancelQueries({ queryKey: issueKeys.list(wsId) })` — fire-and-forget (existing pattern in `mutations.ts`, see comment at line 132). Cancels any in-flight refetches that might land between optimistic update and server response.
   b. `qc.setQueryData(...)` — patches the issue in the list cache (existing).
   c. The WS event for this move arrives later (the user's own WS connection echoes it back) and triggers `qc.invalidateQueries(...)` which is now safe — the cache is already in the right state.
4. **WS event from ANOTHER tab (or another user) during drag.** Such events fire WS handlers in `packages/core/issues/ws-updaters.ts` which call `qc.setQueryData(...)` to patch the cache with the server's truth. Because v0.4 owns the visual reorder via `useSortable`'s ref-tracked transforms (NOT via React state derived from `issues`), a cache mutation does NOT cause the dragging card to jump. The card's transform is live; the `issues` array reference change is irrelevant to the card's render position until drag ends.
5. **Drag-freeze frame after drag end.** Keep the existing `recentlyMovedRef` pattern: after `onDragEnd` fires, set `recentlyMovedRef.current = true` and schedule a `requestAnimationFrame` to flip it back to false. During that frame, the `issues` → `columns` derivation in the `useEffect` (which runs when `issues` changes) is GATED on `!recentlyMovedRef.current`. This prevents a WS-event invalidation that lands on the SAME frame as the drag end from snapping the card back to its old position before the optimistic update propagates.

## WS Race Immunity — Mechanism Summary

The combination of three things makes WS race immunity work:

1. **`useUpdateIssue` calls `qc.cancelQueries` in `onMutate` synchronously** (existing). Any in-flight refetch is aborted before the optimistic patch lands.
2. **`@dnd-kit/react` v0.4 owns visual transforms via refs, not via React state derived from `issues`** (NEW with v0.4 architecture). A WS-event-driven `setQueryData` does not cause the dragging card to re-render at a stale position because the card's visual position is computed from the live drag transform, not from `issues[i].status`.
3. **`recentlyMovedRef` drag-freeze frame** (existing pattern, kept). The 1-frame window after `onDragEnd` blocks the `issues → columns` re-derivation, giving the optimistic cache update time to propagate down through the React tree before any WS-event invalidation can revert the visible position.

If any one of these three is missing, KBN-01 regresses. The checker MUST verify all three are in the implementation before signing off.
