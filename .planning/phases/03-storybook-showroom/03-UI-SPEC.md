# Phase 3 — UI Design Contract

> Visual and interaction contract for the Storybook Showroom (`apps/showroom`) and its atom story renders. Generated by gsd-ui-researcher; verified by gsd-ui-checker.
>
> **Scope shape note.** This phase delivers a developer-facing review sandbox, not a designed product screen. The "UI" surface is therefore split into two layers:
>
> 1. **Storybook chrome** — almost entirely stock (the official Storybook 9 UI). The showroom restricts itself to two configuration knobs (theme global + a11y panel) and one CSS chain (Phase 1 tokens piped into the preview iframe). Nothing else about the chrome is redesigned.
> 2. **Story renders** — the *content* of each story, i.e. how each Phase 2 atom is laid out inside the preview iframe so its variant matrix is visible at a glance. This layer DOES carry a design contract (spacing, typography, copy labels) — but it MUST consume only the tokens already shipped in Phase 1 and the atoms already shipped in Phase 2. Zero new tokens. Zero new atoms.
>
> Everything below maps to one of those two layers and explicitly identifies which.

## Spacing Scale

The showroom inherits Phase 1's 8-point spacing scale. These are the values the showroom is *allowed* to use anywhere it lays out a story (variant grids, padding around the preview, gaps between rows).

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| xs | 4px (`gap-1`) | Inside a single atom row — small inline gaps when grouping a label and the rendered atom |
| sm | 8px (`gap-2`, `p-2`) | Variant cell internal padding; gap between a label and the atom it labels |
| md | 16px (`gap-4`, `p-4`) | Default story container padding; gap between rows in a variant matrix |
| lg | 24px (`gap-6`, `p-6`) | Outer page padding around a story render; gap between matrix sections (e.g. "5 colors" vs "with onRemove") |
| xl | 32px (`gap-8`) | Major section breaks within a single story (rare — most stories fit inside one section) |
| 2xl | 48px | Not used in this phase |
| 3xl | 64px | Not used in this phase |

Exceptions: none. Storybook's chrome (sidebar, top toolbar, addon panel) is stock — the showroom does not override those paddings.

**Story container default:** `p-6 flex flex-col gap-6` — predictable outer frame so every story renders against the same background-padding surface. This is the *only* layout primitive the showroom contributes.

## Typography

The showroom adds NO new font sizes. Story labels and section headers (used inside the preview iframe to title variant rows) reuse Phase 1's existing scale. All sizes resolve through the shared font stack defined by `apps/showroom/.storybook/preview.tsx` (Inter via fontsource).

| Role | Tailwind class | Computed | Weight | Line height | Used by |
|------|---------------|----------|--------|-------------|---------|
| Section header | `text-sm` | 14px | `font-semibold` (600) | `leading-5` (1.43) | Heading above each variant matrix in a story (e.g. "Colors", "With X-to-remove", "Sizes") |
| Variant label | `text-xs` | 12px | `font-medium` (500) | default | Small label next to each rendered variant (e.g. `tag-p0`, `tag-p1`, `default`, `lg`) |
| Atom-internal text | (inherited from Phase 2 atom) | — | — | — | The atoms themselves render their own text per their Phase 2 contract. The showroom MUST NOT override or re-style atom text. |

**Italic usage:** None of the showroom's chrome text uses italic. Italic is reserved for product display headings (Phase 4 sidebar wordmark, Phase 6 auth titles) — the showroom is a developer tool, not a product surface, and will not borrow that visual signal.

**Numerals:** No tabular numerals required in this phase.

**Font-family token:** `--font-sans` only. The Storybook chrome itself uses Storybook's default UI fonts (the showroom does not theme the manager UI).

## Color

The showroom layer consumes **only** Phase 1 semantic tokens. The 60/30/10 split below describes how the *story canvas* (the preview iframe content area) loads color — not the Storybook chrome (which is stock).

| Role | Token | Usage in this phase |
|------|-------|---------------------|
| Dominant (60%) | `--background` | Story canvas backdrop in light mode (matches what real apps render against). In dark mode, `.dark`-flipped via the theme toggle. |
| Secondary (30%) | `--card`, `--muted-foreground`, `--border` | Variant labels (`text-muted-foreground`); subtle dividers between rows if used (`border-border`); fallback container surfaces if a story needs a bordered card to demonstrate an atom on a non-default surface |
| Accent (10%) | `--brand`, `--tag-p0..p3` | Reserved for the atoms themselves — the showroom NEVER uses brand or tag tokens directly in the story chrome. These tokens enter the canvas only through the rendered atoms. |
| Destructive | `--destructive` | NOT used directly by the showroom — semantic destructive colors only appear via `tag-p0` on a `TagChip` (which already maps to the destructive hue per Phase 1 D-08). |
| Focus ring | `--ring` | Inherited from atoms — the showroom does not focus-ring its own elements (nothing in the showroom chrome is focusable beyond stock Storybook controls). |

**Accent reserved for:**
- The atoms themselves (TagChip fills, AccentBar segments, AvatarInitial circles, SegmentedControl active item lift). The showroom's variant grid, labels, and section headers MUST remain neutral (`text-foreground` / `text-muted-foreground` only).

**Light + dark mode contract (load-bearing for SC#2):**
- The theme toggle in the Storybook toolbar MUST flip a class (`.dark`) on the preview iframe's document element (or on the immediate ancestor of the story root, depending on which decorator approach is chosen). The class location MUST match what Tailwind's `@custom-variant dark (&:is(.dark *))` rule (declared in `apps/web/app/globals.css` and to be mirrored in the showroom's preview CSS) resolves against — otherwise dark variants of token-backed utilities won't fire and `bg-sidebar` will appear transparent (the failure mode SC#2 explicitly calls out).
- Verification gate: a "tokens smoke" story renders a row of token-backed surfaces (`bg-sidebar`, `bg-card`, `bg-muted`, `bg-tag-p0..p3`, `bg-brand`) and a developer flips the toggle. Every surface must visibly change. This story is required.

**No hex / no RGB inside the showroom code.** The showroom inherits the no-hardcoded-color contract from Phase 1. All colors flow through tokens.

## Copywriting Contract

The Storybook Showroom is a developer surface. Its strings are short, structural labels — NOT product copy — and are English source-of-truth (matches the atom-level English convention from Phase 2 UI-SPEC).

| Element | Copy |
|---------|------|
| Primary CTA | (none — Storybook owns its own toolbar; the showroom adds no CTAs) |
| Empty state heading | (none — every story is curated; there is no empty state in a story) |
| Empty state body | (none) |
| Error state | (none — Storybook surfaces its own errors via the addons panel; the showroom does not own an error UI) |
| Destructive confirmation | (none — no destructive actions in this phase) |
| Theme toolbar control title | `"Theme"` |
| Theme toolbar control items | `"Light"`, `"Dark"` (in this order) — the toolbar control is a 2-position toggle, NOT the 3-radio Light/Dark/System pattern from Phase 1 D-13 (which is product-level; Storybook is dev-tool-level and only needs to verify the two end-states) |
| Section header copy (per story) | `"Colors"` (TagChip, AccentBar), `"With X-to-remove"` (TagChip), `"Sizes"` (AvatarInitial), `"Determinism"` (AvatarInitial — renders the same name 5 times to visually confirm color stability), `"Segments"` (AccentBar — renders 1/2/3/4-segment variants), `"Orientation"` (AccentBar — horizontal vs vertical), `"States"` (SegmentedControl — default / disabled item / focused via Tab) |
| Variant label format | Token-or-prop-name verbatim (e.g. `tag-p0`, `brand`, `default`, `lg`, `2 segments`). Lowercase, monospace where it improves scannability (use `font-mono` from the existing token set if a planner judges it readable; default is `font-sans`). |
| Storybook story `title` (sidebar tree) | `"Atoms / TagChip"`, `"Atoms / AccentBar"`, `"Atoms / AvatarInitial"`, `"Atoms / SegmentedControl"`, `"Foundations / Tokens"` (the smoke-test story for SC#2). |
| Storybook story name (per `Story` export) | `"Default"` for the canonical example; named variants for matrix-style stories (`"AllColors"`, `"WithRemove"`, `"AllSizes"`, etc.). Stick to single PascalCase identifiers. |

**Language:** English source-of-truth. No bilingual de/en in the showroom — same rationale as Phase 2 atom-level strings (structural, short, English-only).

**Internationalization seam:** None. Story labels are not user-facing.

**Acceptance phrasing for SC#2 verification step (in the smoke story description):** `"Toggle the Theme control in the toolbar. Every surface below must visibly change. If `bg-sidebar` stays transparent in dark mode, the dark-class target is wrong."` — this is the developer-facing instruction baked into the story so a future contributor can self-verify.

## Mocked Providers Contract (load-bearing for SB-02 + SC#1)

## Light + Dark Mode Verification Gate (SC#2)

| Step | Expected Outcome |
|------|------------------|
| 1. Open `Foundations / Tokens / Surfaces`. | Smoke story renders all token swatches in light mode. |
| 2. Click the Theme control in the toolbar; switch to "Dark". | Every swatch visibly changes. `bg-sidebar` swatch is now deep-forest-green (dark sidebar token), NOT transparent. `bg-card` is now `oklch(0.24 0.013 250)`. `bg-background` is now `oklch(0.18 0.012 250)`. |
| 3. Open each `Atoms / *` story; toggle Theme back and forth. | Atom colors adapt purely via tokens (no `dark:*` classes inside the atoms). TagChip P0 stays red in both modes; AvatarInitial circle hue may shift slightly (token-driven); SegmentedControl track shifts from light `bg-muted` to dark `bg-muted`. |
| 4. Check the a11y panel. | Zero critical violations on every atom story. |

**If the toggle does not flip `bg-sidebar` correctly:** the decorator is targeting the wrong DOM ancestor. Move the class to `document.documentElement` (the iframe `<html>`). This is the canonical mistake the smoke story is designed to catch.

## Hard Constraints Summary (consumed by gsd-ui-checker)

1. **No mocked atom implementations.** Stories import the real atom from `@multica/ui/components/ui/{name}`. Mocking only applies to providers (and the providers are *omitted entirely*, not mocked, per the table above).
2. **No new design tokens.** Every color, radius, font, and spacing value resolves through Phase 1 tokens.
3. **No `next/*`, no `react-router-dom`, no `@multica/core`.** The `apps/showroom/package.json` MUST NOT list these as dependencies. CI typecheck breakage if violated.
4. **No hardcoded colors.** Same rule as the rest of the codebase. No `#`-prefix color literals; no `rgb(...)`; no `text-red-500` Tailwind defaults.
5. **No story-level dark-mode override.** Atoms themselves must be dark-mode-correct via tokens. If a story needs `dark:` overrides to look right, the *atom* is broken and Phase 2 must be reopened — the story is not the place to patch.
6. **Storybook chrome is stock.** No theming the manager UI; no custom panels; no rebrand of the Storybook header. The showroom is a developer tool, not a designed product surface.
7. **Story file location.** All stories live in `apps/showroom/stories/`. No `*.stories.tsx` in `packages/ui/`.
8. **Theme toggle = `globalTypes` decorator OR `@storybook/addon-themes` `withThemeByClassName` — pick one.** Document the choice inline.
9. **a11y panel is mandatory.** `@storybook/addon-a11y` configured at WCAG 2.1 AA. Cannot be opt-in per story.
10. **Smoke story `Foundations / Tokens / Surfaces` is required** (see SC#2 verification gate above).
