# Phase 5.1: Auth Backend Endpoints (INSERTED) — Research

**Researched:** 2026-04-25
**Domain:** Go HTTP backend (Chi router, sqlc/pgx, Resend) — password-based auth
**Confidence:** HIGH (existing OTP/PAT machinery is the template; minimal unknowns)

## Summary

Phase 5.1 layers password-based auth on top of the existing OTP-only machinery in `server/internal/handler/auth.go`. The codebase already has every primitive we need: bcrypt-equivalent hashing patterns (`auth.HashToken` for SHA-256 token storage on Personal Access Tokens), `crypto/rand` token generation (`auth.GeneratePATToken`), `subtle.ConstantTimeCompare` for time-safe comparison, `EmailService` (Resend SDK) with HTML/subject-injection hardening, JWT issuance + cookie set (`auth.SetAuthCookies`), DB-backed rate limiting (`GetLatestCodeByEmail` + 60s gate), idempotent fixture-based integration tests against a real PostgreSQL (`handler_test.go`). What does **not** yet exist: bcrypt as a dependency, password column on `user`, reset/verify token columns, and the five new endpoints.

The endpoints add five POST routes under the existing public `/auth/*` group (NOT `/api/auth/*` — see Pitfall 1). Migration `059_add_password_auth_to_users.up.sql` adds six nullable columns to `"user"`. Tokens are 256-bit `crypto/rand` → URL-safe base64; the **hash** (SHA-256 hex) is stored in DB with an expiry column; comparison hashes the incoming token and looks up by hash. Existing OTP/Google flows remain untouched — `password_hash` stays nullable so OTP-only and Google-only users keep working.

**Primary recommendation:** Mirror the existing PAT pattern (random token in code, hashed in DB, `subtle.ConstantTimeCompare`-equivalent via DB-side equality on the hash) for both reset and verify tokens. Mirror the existing `SendCode` handler shape (decode → normalize email → DB rate-limit check → DB write → email-send → JSON response) for the three "request-side" endpoints (signup, password-reset/request, email-verify/resend). Hardcode no new email infrastructure — extend `service/EmailService` with three new methods (`SendPasswordResetEmail`, `SendEmailVerification`, `SendSignupVerification`) following the `buildInvitationParams` pattern (HTML escape + subject sanitize + rune-cap).

## Architectural Responsibility Map

Phase 5.1 is single-tier (Go API). All capabilities live in the API layer.

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Password hashing | API / Backend | — | bcrypt cost 12 — server-only; never ship hash to client |
| Token generation (reset, verify) | API / Backend | — | `crypto/rand` requires server-side RNG; tokens go out via email only |
| Token storage (hashed) | Database / Storage | — | Columns on `user` table, never returned in API responses |
| Email delivery | API / Backend → Resend SaaS | — | Existing `EmailService` already wired; new methods follow the same pattern |
| Rate limiting (per-email) | Database / Storage | API / Backend | DB-backed (mirrors existing `GetLatestCodeByEmail` 60s gate) — multi-instance safe |
| Session issuance after signup | API / Backend | — | `auth.SetAuthCookies` + `issueJWT` — same as VerifyCode |
| Session token validation | API / Backend (middleware) | — | Existing `middleware.Auth` — untouched by this phase |

**Tier sanity:** Phase 5.1 has **zero** frontend touch points. Phase 6 owns all `apps/web/app/(auth)/*` and `packages/views/auth/*` work. The API client (`packages/core/api/client.ts`) gets new methods in Phase 6, **not** here.

## DB Schema Delta

Migration filename (next sequential): `059_add_password_auth_to_users.up.sql` + `059_add_password_auth_to_users.down.sql`

### Up migration

```sql
-- Add password-based auth + email verification + password reset to users.
-- All columns are nullable so existing OTP-only and Google-only users remain
-- valid. password_hash is set on signup or password-reset/confirm; email
-- verification timestamp is set on email-verify; reset/verify tokens are
-- transient and cleared after use.

ALTER TABLE "user"
  ADD COLUMN password_hash TEXT,
  ADD COLUMN email_verified_at TIMESTAMPTZ,
  ADD COLUMN password_reset_token_hash TEXT,
  ADD COLUMN password_reset_expires_at TIMESTAMPTZ,
  ADD COLUMN email_verify_token_hash TEXT,
  ADD COLUMN email_verify_expires_at TIMESTAMPTZ;

-- Lookup index for password-reset/confirm: query is "SELECT WHERE
-- password_reset_token_hash = $1 AND password_reset_expires_at > now()".
-- Partial index on non-null hash keeps the index small (most users have NULL).
CREATE INDEX idx_user_password_reset_token_hash
  ON "user"(password_reset_token_hash)
  WHERE password_reset_token_hash IS NOT NULL;

CREATE INDEX idx_user_email_verify_token_hash
  ON "user"(email_verify_token_hash)
  WHERE email_verify_token_hash IS NOT NULL;
```

### Down migration

```sql
-- WARNING: Dropping these columns is destructive — any user accounts created
-- via password signup after this migration ran will lose their password_hash
-- and become unable to log in via password until they re-register.
-- This down migration is intended for development rollback only.

DROP INDEX IF EXISTS idx_user_email_verify_token_hash;
DROP INDEX IF EXISTS idx_user_password_reset_token_hash;

ALTER TABLE "user"
  DROP COLUMN IF EXISTS email_verify_expires_at,
  DROP COLUMN IF EXISTS email_verify_token_hash,
  DROP COLUMN IF EXISTS password_reset_expires_at,
  DROP COLUMN IF EXISTS password_reset_token_hash,
  DROP COLUMN IF EXISTS email_verified_at,
  DROP COLUMN IF EXISTS password_hash;
```

### Schema design notes (HIGH confidence)

- **All columns nullable** — required so existing OTP-only and Google-only users (who have no password) remain valid. The signup handler enforces non-null `password_hash` for password-auth signups; OTP and Google login paths never read `password_hash`.
- **Tokens stored as SHA-256 hex** — never plaintext. Naming convention `*_token_hash` makes it explicit at the schema level. [CITED: OWASP Forgot Password Cheat Sheet — "Stored in a secure manner"]
- **Hash uses `auth.HashToken`** — the existing helper hashes to lowercase hex (64 chars). Reuse it; don't introduce a parallel hashing function.
- **Indexes are partial** — `WHERE NOT NULL` keeps them small since most users have NULL token hashes (tokens are transient).
- **Existing constraint check:** `user.email TEXT UNIQUE NOT NULL` exists from `001_init.up.sql`. No conflict with new columns. `password_hash` does NOT need a unique constraint.
- **`email_verified_at TIMESTAMPTZ`** — nullable; non-null means verified. Mirrors the existing `onboarded_at TIMESTAMPTZ` pattern (`COALESCE(onboarded_at, now())`).

### sqlc regen needed

After adding the migration, run `make sqlc` (which calls `cd server && sqlc generate`). This updates `server/pkg/db/generated/user.sql.go` to include the new columns on the `User` struct + scan calls. **Wave 0** of the plan must include this regen step — every subsequent task that uses `db.User` will reference the new fields.

### New sqlc queries (additions to `server/pkg/db/queries/user.sql`)

```sql

INSERT INTO "user" (name, email, password_hash, email_verify_token_hash, email_verify_expires_at)
VALUES ($1, $2, $3, $4, $5)
```

## Endpoint Specifications

All endpoints mount under the existing **public** route group at `/auth/*` (NOT `/api/auth/*` — see Pitfalls §1). Order in `server/cmd/server/router.go` lines 150-154 — append after `/auth/logout`.

### 1. `POST /auth/signup`

**Request body:**
```json
{ "email": "user@example.com", "password": "atLeast12chars", "name": "Display Name" }
```

**Response 200 (success):**
```json
{
  "token": "<JWT>",
  "user": { /* UserResponse — same shape as VerifyCode */ }
}
```
Sets `multica_auth` HttpOnly cookie + `multica_csrf` cookie via `auth.SetAuthCookies`.

**Response 400** — invalid body, missing field, password too short
**Response 403** — `checkSignupAllowed` returned `ErrSignupProhibited` / `ErrEmailNotAllowed`
**Response 409** — email already registered (intentional disclosure on signup; differs from password-reset where we hide existence — this is acceptable per OWASP since signup forms inherently leak whether an email exists via "email taken" feedback)
**Response 500** — bcrypt failure, DB failure, email-send failure (logged; user gets generic message)

**Idempotency:** Not idempotent. Each successful call creates exactly one user.

**Rate limiting:** Per-email DB-backed (mirror `SendCode`'s 60s window via a new `GetLatestSignupAttemptByEmail` query) OR rely on email-send failure path. **Recommend:** check for existing `user` row by email first (returns 409); rate-limit by IP at the chi router level via `chimw.Throttle` if planner adds it. (Open Question §1.)

**Behavior:**
1. Decode body, lowercase+trim email, validate fields (email shape via simple `strings.Contains(email, "@")` check or stdlib `net/mail.ParseAddress`).
2. Validate password: minimum length 12 chars (recommend; CONTEXT defers complexity to planner). Max length 72 bytes (bcrypt hard limit — see Pitfalls §1).
3. Call `checkSignupAllowed(email, true)` to honor `ALLOW_SIGNUP` flag. Return 403 on rejection.
4. Lookup user by email — if found, return 409 "email already registered".
5. `bcrypt.GenerateFromPassword([]byte(password), 12)` → `password_hash`.
6. Generate verify token: `crypto/rand.Read(32 bytes)` → `base64.RawURLEncoding.EncodeToString(...)` → 43-char URL-safe token.
7. Hash the verify token via `auth.HashToken(token)`.
8. Insert user via `CreateUserWithPassword` with hash + email_verify_token_hash + email_verify_expires_at = now+24h.
9. `findOrCreateUser` is **NOT** used here — signup is its own path (we want non-existence to be a hard error, not a silent create).
10. Send signup verification email via `EmailService.SendSignupVerification(email, verifyToken)` with link `{FRONTEND_ORIGIN}/auth/verify-email?token={verifyToken}`.
11. Capture analytics signup event with `auth_method: "password"`.
12. Issue JWT, set cookies, return `LoginResponse`.

### 2. `POST /auth/password-reset/request`

**Request body:**
```json
{ "email": "user@example.com" }
```

**Response 200 (always, even for unknown emails):**
```json
{ "message": "If an account exists for this email, a reset link has been sent." }
```

**Response 400** — invalid body, missing email
**Response 429** — rate limit (per-email; share/extend `GetLatestCodeByEmail` shape)
**Response 500** — DB failure (logged; user gets generic 500 to avoid leaking)

**Idempotency:** Idempotent for the response shape. Multiple calls within rate window all return 200; only one email is sent (rate-limited).

**Rate limiting:** REQUIRED. Per-email: max 1 request per 60 seconds (mirror OTP `SendCode`). Implementation: store the timestamp in the `password_reset_expires_at` field (since we set it to `now()+1h`, we can check "if expires_at - 59min > now()" → "less than 60s since last request"). Cleaner: add a separate `password_reset_requested_at` column, OR add a "GetUserByEmail" → check `(password_reset_expires_at - 59m).After(now())` in handler logic.

**Behavior:**
1. Decode body, lowercase+trim email.
2. Lookup user by email. If not found → return 200 immediately (no email sent, but indistinguishable response). [CITED: OWASP Forgot Password Cheat Sheet — consistent message]
3. **Timing-attack mitigation:** even if user is not found, optionally call `bcrypt.GenerateFromPassword` on a dummy value to equalize response time. (LOW priority — add if planner decides.)
4. Check rate limit (60s per email) → return 429 if exceeded.
5. Generate reset token: `crypto/rand.Read(32)` → base64url.
6. Hash via `auth.HashToken`.
7. Call `SetPasswordResetToken(userID, hash, expiresAt = now+1h)`.
8. Send reset email via `EmailService.SendPasswordResetEmail(email, resetToken)` with link `{FRONTEND_ORIGIN}/auth/reset-password?token={resetToken}`.
9. Return 200.

### 3. `POST /auth/password-reset/confirm`

**Request body:**
```json
{ "token": "<base64url token from email>", "newPassword": "atLeast12chars" }
```

**Response 200:**
```json
{ "message": "Password updated. Please log in." }
```
Note: does NOT auto-issue session; user is forced through normal login. (Pattern matches Linear, GitHub. Avoids handing a session to whoever clicked the email — adversary may have brief access to the inbox.)

**Response 400** — invalid body, missing fields, weak password
**Response 401** — invalid or expired token
**Response 500** — bcrypt failure, DB failure

**Idempotency:** Single-use. Once confirmed, the token is cleared (`password_reset_token_hash = NULL`) and a second confirm with the same token returns 401.

**Behavior:**
1. Decode body. Validate password strength (min 12 chars, max 72 bytes — see Pitfalls §1).
2. `auth.HashToken(token)` → lookup hash.
3. Call `GetUserByPasswordResetTokenHash(hash)` — sqlc query already filters `expires_at > now()`. If `pgx.ErrNoRows` → return 401 "invalid or expired token".
4. `bcrypt.GenerateFromPassword([]byte(newPassword), 12)` → new hash.
5. Call `ConfirmPasswordReset(userID, newHash)` — atomically updates password + clears reset token.
6. **Optional but recommended:** invalidate any active sessions. Currently sessions are stateless JWTs (30-day exp), so true invalidation needs a `password_changed_at` column + JWT validation that rejects tokens issued before that timestamp. **Not in CONTEXT scope** — flag in Open Questions §2.
7. Return 200.

### 4. `POST /auth/email-verify`

**Request body:**
```json
{ "token": "<base64url token from email>" }
```

**Response 200:**
```json
{ "message": "Email verified." , "user": { /* UserResponse */ } }
```

**Response 400** — invalid body, missing token
**Response 401** — invalid or expired token
**Response 500** — DB failure

**Idempotency:** Single-use per token. If user is already verified (`email_verified_at IS NOT NULL`) and token is invalid (cleared), returns 401. The `COALESCE(email_verified_at, now())` in `ConfirmEmailVerification` keeps the original verification timestamp on duplicate-safe replays before clearing.

**Behavior:**
1. Decode body.
2. `auth.HashToken(token)` → lookup hash.
3. Call `GetUserByEmailVerifyTokenHash(hash)` — filters by `expires_at > now()`. If not found → 401.
4. Call `ConfirmEmailVerification(userID)` — sets `email_verified_at`, clears token columns.
5. Return 200 with updated user.

**Note:** This endpoint is **public** (no auth middleware). Anyone with a valid token can verify the associated account — that is the intent. The token IS the auth here.

### 5. `POST /auth/email-verify/resend`

**Request body:**
```json
{ "email": "user@example.com" }
```

**Response 200 (always, even for unknown / already-verified emails):**
```json
{ "message": "If an account exists, a new verification link has been sent." }
```

**Response 400** — invalid body, missing email
**Response 429** — rate limited
**Response 500** — DB failure

**Idempotency:** Same response shape regardless of email existence or verification state.

**Rate limiting:** REQUIRED. Per-email: max 1 per 60 seconds. Same pattern as `password-reset/request`.

**Behavior:**
1. Decode body, normalize email.
2. Lookup user. If not found → return 200.
3. If `email_verified_at IS NOT NULL` → return 200 (no email sent — already verified, no work to do).
4. Check rate limit → 429 if exceeded.
5. Generate new verify token; hash; call `SetEmailVerifyToken(userID, hash, now+24h)` (overwrites any existing token — that's the desired behavior for resend).
6. Send email via `EmailService.SendEmailVerification(email, verifyToken)`.
7. Return 200.

**Should NOT use any auth middleware** — user may not be logged in when clicking "Resend verify" from an "Email not verified" banner.

## Token Strategy

| Token Type | Bytes | Encoding | Hashed in DB | Expiry | Lifetime |
|------------|-------|----------|--------------|--------|----------|
| Email verify | 32 (256-bit) | `base64.RawURLEncoding` (43 chars, no padding, URL-safe) | `auth.HashToken` (SHA-256 hex, 64 chars) | 24 hours | One-time (cleared on confirm or on resend) |
| Password reset | 32 (256-bit) | `base64.RawURLEncoding` | `auth.HashToken` | 1 hour | One-time (cleared on confirm) |

### Generation pattern (mirror `auth.GeneratePATToken` shape)

```go
// server/internal/auth/jwt.go — append to existing file
func GenerateAuthToken() (string, error) {
    b := make([]byte, 32) // 256 bits
    if _, err := rand.Read(b); err != nil {
        return "", fmt.Errorf("generate auth token: %w", err)
    }
    return base64.RawURLEncoding.EncodeToString(b), nil
}
```

This is generic enough to use for both reset and verify (no need for two separate functions). The token's *purpose* is determined by which DB column it's stored in.

### Verification pattern

```go
// In handler:
incomingTokenHash := auth.HashToken(req.Token)
user, err := h.Queries.GetUserByPasswordResetTokenHash(r.Context(), incomingTokenHash)
if err != nil {
    if isNotFound(err) {
        writeError(w, http.StatusUnauthorized, "invalid or expired token")
        return
    }
    writeError(w, http.StatusInternalServerError, "failed to verify token")
    return
}
// expiry check is done in the SQL: WHERE password_reset_expires_at > now()
```

**`subtle.ConstantTimeCompare` is NOT needed at the application layer here** — the comparison is `WHERE token_hash = $1` in PostgreSQL, which is constant-time on a 64-char fixed-length hex string within practical attack budgets. The OTP path uses `subtle.ConstantTimeCompare` because the comparison is in Go (`code == dbCode.Code`); ours is in SQL. [CITED: existing pattern in `auth.go:315` for OTP — they only need it because comparison is in Go]

### Token invalidation

- **Reset token** — cleared in `ConfirmPasswordReset` SQL (sets `password_reset_token_hash = NULL`).
- **Verify token** — cleared in `ConfirmEmailVerification` SQL.
- **Resend overrides** — `SetEmailVerifyToken` overwrites any existing token (any in-flight email's token becomes invalid).
- **Reset request overrides** — `SetPasswordResetToken` overwrites any existing reset token (so if a user requests reset twice, only the latest link works — this is the desired UX).

### Pattern 2: Token Hash + Lookup

**What:** Generate token in code, store hash in DB, lookup by hash.

**When to use:** Any single-use, time-bound credential (reset, verify, PAT, daemon token).

**Example:** See `personal_access_token.go:79-89` and `middleware/auth.go:47-50` for the existing hash-store-lookup pattern.

### Pattern 3: Idempotent Response (Email Enumeration Prevention)

**What:** Endpoints that accept an email and trigger an email-send return the same status + message regardless of whether the email exists.

**When to use:** Password reset request, resend verification, any "by email" trigger.

**Reference:** OWASP Forgot Password Cheat Sheet — "Return a consistent message for both existent and non-existent accounts." [CITED]

**Counter-example:** Signup endpoint INTENTIONALLY returns 409 for already-registered emails — this is acceptable because signup forms inherently leak existence (UX requires it). The asymmetry is documented in OWASP guidance.

### Anti-Patterns to Avoid

- **Storing tokens plaintext** — never `password_reset_token TEXT NOT NULL` without hash. Tokens are credentials.
- **Auto-login after password reset** — do not issue a JWT in the `password-reset/confirm` response. Adversary with brief inbox access shouldn't get a long-lived session.
- **Reusing OTP `verification_code` table for verify/reset tokens** — schema mismatch (OTP is 6 digits, verify token is 256-bit base64). Separate columns on `user` are right.
- **Calling `findOrCreateUser` from signup** — that helper silently creates users; signup must error on existing email so we don't overwrite their account.
- **bcrypt cost too high** — cost 14+ approaches 1s on commodity hardware. Cost 12 (~250ms) is the OWASP sweet spot. [ASSUMED: latency from training; verify in plan via benchmark.]
- **Comparing hashes with Go `==`** — fine for fixed-length hex (constant-time in practice for 64 chars) but better to delegate to SQL `WHERE` (which is a single op). The OTP path uses `subtle.ConstantTimeCompare` because it compares variable-input strings in Go.
- **Skipping `checkSignupAllowed` on `/auth/signup`** — would bypass the `ALLOW_SIGNUP=false` flag. Self-hosted operators rely on this.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Password hashing | Custom SHA-256 + salt | `golang.org/x/crypto/bcrypt` | bcrypt has built-in salt, cost-tunable, time-tested; SHA-256 is too fast → vulnerable to GPU attacks |
| Random token generation | `math/rand` | `crypto/rand` (existing pattern) | `math/rand` is not CSPRNG; tokens MUST come from CSPRNG to be unpredictable |
| Token URL encoding | `hex` | `base64.RawURLEncoding` | hex is 2x longer for the same entropy; base64url is shorter and URL-safe without padding |
| Time-safe comparison | `bytes.Equal` for sensitive comparisons | DB-side `WHERE hash = $1` (this phase) or `subtle.ConstantTimeCompare` (variable inputs) | Go `==` and `bytes.Equal` short-circuit; vulnerable to timing analysis on user-controlled inputs |
| Email delivery | New SMTP/Mailgun client | Existing `service.EmailService` (Resend) | Already wired with API key handling, dev-mode fallback (prints to stdout), HTML-escape pattern, subject sanitization |
| JWT issuance | Custom signed string | Existing `auth.issueJWT` + `auth.JWTSecret()` | Already validated by `middleware.Auth`; reuse keeps signature verification consistent |
| Cookie setting | `http.SetCookie` directly | `auth.SetAuthCookies` | Handles HttpOnly, Secure, Domain, SameSite, CSRF cookie all in one — easy to get wrong piecemeal |
| Rate limiting | Per-process map | DB-backed timestamp check (existing pattern) | Multi-instance safe; survives restarts |
| Email enumeration prevention | Custom logic | Mirror existing `SendCode` shape + return constant message | OWASP-blessed approach |

**Key insight:** Every primitive needed already exists in the codebase except bcrypt itself. The phase is a **composition** task, not an invention task.

## Common Pitfalls

### Pitfall 1: Route prefix is `/auth/*` not `/api/auth/*`
**What goes wrong:** CONTEXT.md success criteria specify `POST /api/auth/signup`, but the existing OTP routes (`/auth/send-code`, `/auth/verify-code`, `/auth/google`, `/auth/logout`) are mounted at the root `/auth/*` (NOT `/api/auth/*`). See `server/cmd/server/router.go:151-154`.
**Why it happens:** Router has `/api/*` for protected/workspace routes and `/auth/*` for public auth — historical convention.
**How to avoid:** Mount new endpoints at `/auth/signup`, `/auth/password-reset/request`, `/auth/password-reset/confirm`, `/auth/email-verify`, `/auth/email-verify/resend`. Update CONTEXT.md / success-criteria language to match. **The frontend (Phase 6) must also use `/auth/...`** — the API client in `packages/core/api/client.ts` will reflect the actual mount.
**Warning signs:** Plans referencing `/api/auth/...` are using the CONTEXT spelling; correct to `/auth/...` before merge.

### Pitfall 2: bcrypt 72-byte input cap
**What goes wrong:** `bcrypt.GenerateFromPassword` truncates passwords longer than 72 bytes silently (well, it returns `ErrPasswordTooLong` in modern versions — verify in `golang.org/x/crypto v0.50.0`). Users with 73+ char passwords either fail signup or get an unexpectedly truncated hash.
**Why it happens:** bcrypt algorithm limitation — input is fed through Blowfish key schedule which uses only first 72 bytes.
**How to avoid:** Validate `len([]byte(password)) <= 72` in the signup and password-reset/confirm handlers. Return 400 with a clear message ("Passwort darf maximal 72 Bytes umfassen"). Recommend min 12, max 72.
**Warning signs:** Tests pass but production users with long passphrases can't log in.
[CITED: pkg.go.dev/golang.org/x/crypto/bcrypt — "Does not accept passwords longer than 72 bytes."]

### Pitfall 3: Email enumeration via differential responses
**What goes wrong:** If `password-reset/request` returns 404 for unknown emails and 200 for known ones, attackers harvest valid emails by probing.
**Why it happens:** Natural temptation to "be helpful" — return "no account found" so real users know to sign up.
**How to avoid:** Always return 200 with the same generic message. The signup endpoint is allowed to return 409 because signup forms inherently leak existence in the UX.
[CITED: OWASP Forgot Password Cheat Sheet — "Return a consistent message"]
**Warning signs:** Tests assert different status codes for known vs unknown emails on `/auth/password-reset/request`.

### Pitfall 4: Email enumeration via differential timing
**What goes wrong:** Even with identical responses, if "user found" path takes 200ms (DB write + email send) and "user not found" takes 5ms (single SELECT), attackers can timing-side-channel.
**Why it happens:** Real work only happens for known emails.
**How to avoid:** For `/auth/password-reset/request` specifically, optionally execute a no-op `bcrypt.GenerateFromPassword` on a dummy value to equalize timing. This is **MEDIUM** priority — the existing OTP `SendCode` handler does NOT do this and ships fine. Flag in Open Questions §4.
**Warning signs:** Differential timing observable from external timing measurement.

### Pitfall 5: Reset token reuse
**What goes wrong:** User's reset email link is intercepted (corporate proxy, shared inbox) or the user forwards it. If we don't invalidate the token after first use, the attacker can reset the password again later.
**How to avoid:** `ConfirmPasswordReset` SQL query atomically clears `password_reset_token_hash` to NULL. Subsequent lookups by that hash return ErrNoRows → 401. **Already designed into the schema.**
**Warning signs:** Test the same token twice in a row — second call must 401.

### Pitfall 6: Password-reset auto-login
**What goes wrong:** If `/auth/password-reset/confirm` issues a JWT + sets cookies, an attacker with brief inbox access (5 minutes on a public computer) can reset the password AND get an active session.
**How to avoid:** Do NOT call `auth.SetAuthCookies` or return a `Token` in the confirm response. User must explicitly log in afterward.
**Warning signs:** Confirm response contains a token; cookies are set on the response.

### Pitfall 7: Stale sessions after password reset
**What goes wrong:** User suspects compromise, resets password — but old JWTs are still valid for up to 30 days. Adversary keeps the old session.
**How to avoid:** Add `password_changed_at TIMESTAMPTZ` column; have `middleware.Auth` reject JWTs with `iat < user.password_changed_at`. **Out of CONTEXT scope** — flag in Open Questions §2 and Deferred for follow-up phase.
**Warning signs:** Security review flags JWT invalidation. Currently a known limitation of the JWT model.

### Pitfall 8: Password complexity not enforced
**What goes wrong:** Users sign up with `12345678`. Phase 6 has frontend zxcvbn meter (AUTH-02) but backend does not enforce — bypassable by direct API calls.
**How to avoid:** Backend MUST enforce a minimum (recommend ≥ 12 chars). Backend MAY add zxcvbn-equivalent (e.g., `github.com/trustelem/zxcvbn` Go port) but adds dependency weight. **Recommend: simple length check (≥ 12, ≤ 72) on backend; frontend handles UX with zxcvbn.**
**Warning signs:** Direct curl-driven signup with `password: "abc"` succeeds.

### Pitfall 9: Forgetting `make sqlc` regen
**What goes wrong:** Adding new SQL queries to `user.sql` without running `make sqlc` means the Go code can't reference them — compile fails or worse, plans reference nonexistent functions.
**How to avoid:** Wave 0 task includes both migration creation AND `make sqlc` AND committing `pkg/db/generated/user.sql.go`. All subsequent plans assume the regen is done.
**Warning signs:** `db.GetUserByPasswordResetTokenHash undefined` compile error.

### Pitfall 10: Existing OTP login flow regression
**What goes wrong:** Refactoring `auth.go` (e.g., extracting helpers) breaks existing `SendCode`/`VerifyCode` tests in `handler_test.go:814-`.
**How to avoid:** Run the full `handler_test.go` suite after every wave. Append to `auth.go` (or split to new files) — do NOT rewrite existing functions.
**Warning signs:** `TestSendCode`, `TestVerifyCode`, `TestSendCodeRateLimit` red.

### Example 1: Signup handler skeleton

```go
// Source: composition of server/internal/handler/auth.go patterns (SendCode + VerifyCode)
// File: server/internal/handler/auth_password.go

type SignupRequest struct {
    Email    string `json:"email"`
    Password string `json:"password"`
    Name     string `json:"name"`
}

const minPasswordLength = 12
const maxPasswordBytes = 72 // bcrypt hard limit

func (h *Handler) Signup(w http.ResponseWriter, r *http.Request) {
    var req SignupRequest
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        writeError(w, http.StatusBadRequest, "invalid request body")
        return
    }

    email := strings.ToLower(strings.TrimSpace(req.Email))
    name := strings.TrimSpace(req.Name)
    if email == "" || req.Password == "" || name == "" {
        writeError(w, http.StatusBadRequest, "email, password and name are required")
        return
    }
    if len(req.Password) < minPasswordLength {
        writeError(w, http.StatusBadRequest, "password must be at least 12 characters")
        return
    }
    if len(req.Password) > maxPasswordBytes {
        writeError(w, http.StatusBadRequest, "password must be at most 72 bytes")
        return
    }

    // Honor self-host signup gating.
    if err := h.checkSignupAllowed(email, true); err != nil {
        var signupErr SignupError
        if errors.As(err, &signupErr) {
            writeError(w, http.StatusForbidden, signupErr.Error())
            return
        }
        writeError(w, http.StatusForbidden, "user registration is disabled")
        return
    }

    // Reject existing emails (signup is NOT findOrCreate).
    if _, err := h.Queries.GetUserByEmail(r.Context(), email); err == nil {
        writeError(w, http.StatusConflict, "email already registered")
        return
    } else if !isNotFound(err) {
        writeError(w, http.StatusInternalServerError, "failed to check email")
        return
    }

    // Hash password (bcrypt cost 12 — ~250ms on commodity hardware).
    passwordHash, err := bcrypt.GenerateFromPassword([]byte(req.Password), 12)
    if err != nil {
        writeError(w, http.StatusInternalServerError, "failed to hash password")
        return
    }

    // Generate verify token (256-bit URL-safe).
    verifyToken, err := auth.GenerateAuthToken()
    if err != nil {
        writeError(w, http.StatusInternalServerError, "failed to generate token")
        return
    }
    verifyTokenHash := auth.HashToken(verifyToken)

    user, err := h.Queries.CreateUserWithPassword(r.Context(), db.CreateUserWithPasswordParams{
        Name:                  name,
        Email:                 email,
        PasswordHash:          pgtype.Text{String: string(passwordHash), Valid: true},
        EmailVerifyTokenHash:  pgtype.Text{String: verifyTokenHash, Valid: true},
        EmailVerifyExpiresAt:  pgtype.Timestamptz{Time: time.Now().Add(24 * time.Hour), Valid: true},
    })
    if err != nil {
        writeError(w, http.StatusInternalServerError, "failed to create user")
        return
    }

    if err := h.EmailService.SendSignupVerification(email, verifyToken); err != nil {
        slog.Error("failed to send signup verification", "email", email, "error", err)
        // Do NOT fail the signup — user account is created; they can resend later.
    }

    h.Analytics.Capture(analytics.Signup(uuidToString(user.ID), user.Email, signupSourceFromRequest(r)))

    tokenString, err := h.issueJWT(user)
    if err != nil {
        writeError(w, http.StatusInternalServerError, "failed to generate session")
        return
    }

    if err := auth.SetAuthCookies(w, tokenString); err != nil {
        slog.Warn("failed to set auth cookies", "error", err)
    }

    slog.Info("user signed up", append(logger.RequestAttrs(r), "user_id", uuidToString(user.ID), "email", email)...)
    writeJSON(w, http.StatusOK, LoginResponse{
        Token: tokenString,
        User:  userToResponse(user),
    })
}
```

```go
// Source: pattern derived from server/internal/handler/auth.go:211 SendCode +

type PasswordResetRequestRequest struct {
    Email string `json:"email"`
}

func (h *Handler) PasswordResetRequest(w http.ResponseWriter, r *http.Request) {
    var req PasswordResetRequestRequest
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        writeError(w, http.StatusBadRequest, "invalid request body")
        return
    }
    email := strings.ToLower(strings.TrimSpace(req.Email))
    if email == "" {
        writeError(w, http.StatusBadRequest, "email is required")
        return
    }

    // CRITICAL: same response for known and unknown emails.
    const okMessage = "If an account exists for this email, a reset link has been sent."

    user, err := h.Queries.GetUserByEmail(r.Context(), email)
    if err != nil {
        if isNotFound(err) {
            writeJSON(w, http.StatusOK, map[string]string{"message": okMessage})
            return
        }
        writeError(w, http.StatusInternalServerError, "failed to lookup user")
        return
    }

    // Rate limit: 60s per email. If the existing reset token is still
    // less than 59 minutes from expiry, that means the request was made
    // less than 60 seconds ago.
    if user.PasswordResetExpiresAt.Valid &&
        time.Until(user.PasswordResetExpiresAt.Time) > 59*time.Minute {
        writeError(w, http.StatusTooManyRequests, "please wait before requesting another reset")
        return
    }

    resetToken, err := auth.GenerateAuthToken()
    if err != nil {
        writeError(w, http.StatusInternalServerError, "failed to generate token")
        return
    }
    resetTokenHash := auth.HashToken(resetToken)

    if _, err := h.Queries.SetPasswordResetToken(r.Context(), db.SetPasswordResetTokenParams{
        ID:                       user.ID,
        PasswordResetTokenHash:   pgtype.Text{String: resetTokenHash, Valid: true},
        PasswordResetExpiresAt:   pgtype.Timestamptz{Time: time.Now().Add(1 * time.Hour), Valid: true},
    }); err != nil {
        writeError(w, http.StatusInternalServerError, "failed to store reset token")
        return
    }

    if err := h.EmailService.SendPasswordResetEmail(email, resetToken); err != nil {
        slog.Error("failed to send password reset email", "email", email, "error", err)
        // Still return 200 — don't leak email-send failure as a side channel.
    }

    writeJSON(w, http.StatusOK, map[string]string{"message": okMessage})
}
```

```go
type PasswordResetConfirmRequest struct {
    Token       string `json:"token"`
    NewPassword string `json:"newPassword"`
}

func (h *Handler) PasswordResetConfirm(w http.ResponseWriter, r *http.Request) {
    var req PasswordResetConfirmRequest
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        writeError(w, http.StatusBadRequest, "invalid request body")
        return
    }
    if req.Token == "" || req.NewPassword == "" {
        writeError(w, http.StatusBadRequest, "token and newPassword are required")
        return

    if len(req.NewPassword) < minPasswordLength {
        writeError(w, http.StatusBadRequest, "password must be at least 12 characters")
        return
    }
    if len(req.NewPassword) > maxPasswordBytes {
        writeError(w, http.StatusBadRequest, "password must be at most 72 bytes")
        return
    }

    tokenHash := auth.HashToken(req.Token)
    user, err := h.Queries.GetUserByPasswordResetTokenHash(r.Context(), tokenHash)
    if err != nil {
        if isNotFound(err) {
            writeError(w, http.StatusUnauthorized, "invalid or expired token")
            return
        }
        writeError(w, http.StatusInternalServerError, "failed to validate token")
        return
    }

    newHash, err := bcrypt.GenerateFromPassword([]byte(req.NewPassword), 12)
    if err != nil {
        writeError(w, http.StatusInternalServerError, "failed to hash password")
        return
    }

    if _, err := h.Queries.ConfirmPasswordReset(r.Context(), db.ConfirmPasswordResetParams{
        ID:           user.ID,
        PasswordHash: pgtype.Text{String: string(newHash), Valid: true},
    }); err != nil {
        writeError(w, http.StatusInternalServerError, "failed to update password")
        return
    }

    slog.Info("user password reset", append(logger.RequestAttrs(r), "user_id", uuidToString(user.ID))...)
    // INTENTIONAL: do not auto-login. User must POST /auth/send-code or use password to log in.
    writeJSON(w, http.StatusOK, map[string]string{"message": "Password updated. Please log in."})
}
```

### Example 5: Email verify resend (idempotent + rate-limited)

```go
type ResendEmailVerifyRequest struct {
    Email string `json:"email"`
}

func (h *Handler) ResendEmailVerify(w http.ResponseWriter, r *http.Request) {
    var req ResendEmailVerifyRequest
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        writeError(w, http.StatusBadRequest, "invalid request body")
        return
    }
    email := strings.ToLower(strings.TrimSpace(req.Email))
    if email == "" {
        writeError(w, http.StatusBadRequest, "email is required")
        return
    }

    const okMessage = "If an account exists, a new verification link has been sent."

    user, err := h.Queries.GetUserByEmail(r.Context(), email)
    if err != nil {
        if isNotFound(err) {
            writeJSON(w, http.StatusOK, map[string]string{"message": okMessage})
            return
        }
        writeError(w, http.StatusInternalServerError, "failed to lookup user")
        return
    }

    // Already verified → no-op (still return 200 to avoid leaking state).
    if user.EmailVerifiedAt.Valid {
        writeJSON(w, http.StatusOK, map[string]string{"message": okMessage})
        return
    }

    // Rate limit: 60s. If existing token expires more than 23 hours in the future,
    // the last resend was less than 1 hour ago — reject.
    if user.EmailVerifyExpiresAt.Valid &&
        time.Until(user.EmailVerifyExpiresAt.Time) > 23*time.Hour+59*time.Minute {
        writeError(w, http.StatusTooManyRequests, "please wait before requesting another email")
        return
    }

    verifyToken, err := auth.GenerateAuthToken()
    if err != nil {
        writeError(w, http.StatusInternalServerError, "failed to generate token")
        return
    }
    verifyTokenHash := auth.HashToken(verifyToken)

    if _, err := h.Queries.SetEmailVerifyToken(r.Context(), db.SetEmailVerifyTokenParams{
        ID:                    user.ID,
        EmailVerifyTokenHash:  pgtype.Text{String: verifyTokenHash, Valid: true},
        EmailVerifyExpiresAt:  pgtype.Timestamptz{Time: time.Now().Add(24 * time.Hour), Valid: true},
    }); err != nil {
        writeError(w, http.StatusInternalServerError, "failed to store verify token")
        return
    }

    if err := h.EmailService.SendEmailVerification(email, verifyToken); err != nil {
        slog.Error("failed to send verify email", "email", email, "error", err)
    }

    writeJSON(w, http.StatusOK, map[string]string{"message": okMessage})
}
```

```go
// GenerateAuthToken creates an opaque 256-bit URL-safe token suitable for
// password-reset and email-verify links. Returns 43 chars of base64url
// (no padding).
func GenerateAuthToken() (string, error) {
    b := make([]byte, 32) // 256 bits
    if _, err := rand.Read(b); err != nil {
        return "", fmt.Errorf("generate auth token: %w", err)
    }
    return base64.RawURLEncoding.EncodeToString(b), nil
}
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Plaintext password compare | bcrypt with cost-tuning | ~2010s industry standard | Required by OWASP ASVS V2.4 |
| Plaintext reset tokens in DB | SHA-256 hash of token | ~2015 standard practice | Database leak doesn't expose live tokens |
| URL path tokens (`/reset/{token}`) | Query string tokens (`?token=...`) | Best practice ~2020 | Path tokens leak via Referer header to embedded resources / third-party scripts |
| 6-hour reset token expiry | 1-hour reset token expiry | OWASP refresh ~2022 | Reduces window for intercepted-link attacks |
| Auto-login after password reset | Force re-login | OWASP guidance | Adversary with brief inbox access can't get long session |

**Deprecated/outdated:**
- MD5/SHA1 password hashing — both broken; bcrypt/argon2/scrypt only
- "Security questions" as reset mechanism — easily socially engineered; OWASP discourages
- Email sender reputation via SPF only — DKIM + DMARC required for deliverability ~2024+ (Resend handles this transparently)

## Open Questions

1. **Per-IP rate limiting strategy**
   - What we know: Existing pattern is per-email DB-backed (`SendCode` uses 60s window via `GetLatestCodeByEmail`). Redis is in `go.mod` for runtime stores.
   - What's unclear: Whether to add per-IP rate limiting at the chi router level via `chimw.Throttle` or `httprate.LimitByIP` (would need a new dep) or accept per-email-only as sufficient.
   - Recommendation: **Start with per-email only (consistent with OTP).** Plan can layer on per-IP if security review demands it.

2. **JWT invalidation on password reset**
   - What we know: Sessions are stateless 30-day JWTs. Reset doesn't invalidate them.
   - What's unclear: Whether to add `password_changed_at` column + middleware check now, or defer.
   - Recommendation: **Defer.** Out of CONTEXT scope. File as follow-up "Session invalidation on credential change" task.

3. **German vs English email copy**
   - What we know: Existing OTP email is English ("Your Multica verification code"). Project response_language is German for UX prose. Phase 7 will rebrand all "Multica" → "AlgoPlan" anyway.
   - What's unclear: Whether to write new emails in German now, English now (matching existing OTP style), or wait for Phase 7.
   - Recommendation: **English copy with "Multica" branding now**, pending discuss-phase confirmation. Phase 7 already plans to translate + rebrand; doubling the work in 5.1 risks merge conflicts.

4. **Timing-attack mitigation on `/auth/password-reset/request`**
   - What we know: OWASP recommends consistent timing; existing OTP `SendCode` does NOT do this; it ships fine in production.
   - What's unclear: Whether to add a no-op `bcrypt.GenerateFromPassword` on a dummy value when email is unknown.
   - Recommendation: **Skip for parity with OTP.** Add only if security review explicitly flags.

5. **Should `Signup` handler block self-signup with an email already registered via OTP-only flow?**
   - What we know: An existing OTP user has `password_hash IS NULL`. Signup with `{email: existing@otp.com, password: "..."}` would currently 409.
   - Open: Should we instead allow "password upgrade" — verifying via OTP first, then setting password? Or keep strict 409?
   - Recommendation: **Strict 409 is fine for v1.** "Add password to my OTP-only account" is a settings-page feature, not a signup flow.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes | bcrypt cost 12 (V2.4.1); password length 12-72 (V2.1.1, V2.1.2); rate limiting (V2.2.1) |
| V3 Session Management | yes | Existing JWT + HttpOnly cookie + CSRF (V3.1, V3.4) — unchanged by this phase |
| V4 Access Control | partial | Public endpoints by design — no auth middleware needed |
| V5 Input Validation | yes | Email format check, password length check, token shape check |
| V6 Cryptography | yes | bcrypt for passwords (V6.2); SHA-256 for token hashing (V6.2.5); `crypto/rand` for token generation (V6.3); `subtle.ConstantTimeCompare` (V6.2.3) |
| V8 Data Protection | yes | Tokens never stored plaintext; passwords never logged |
| V11 Business Logic | yes | One-time token use, rate limiting, idempotent endpoints prevent enumeration/spam |

### Known Threat Patterns for Go HTTP Auth

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| SQL injection | Tampering | sqlc parameterized queries (existing) — never string-concat SQL |
| Email enumeration | Information Disclosure | Identical response for known/unknown emails on reset/resend (Pitfall §3) |
| Timing-based enumeration | Information Disclosure | Optional dummy bcrypt on unknown email path (Pitfall §4) |
| Reset token reuse | Spoofing | Atomic clear in `ConfirmPasswordReset` SQL (Token Strategy §4) |
| Reset link leak via Referer | Information Disclosure | Token in query string + frontend strips token from URL after use (Phase 6) |
| bcrypt input truncation | Tampering | Explicit `len <= 72` check before `GenerateFromPassword` (Pitfall §2) |
| JWT replay after credential change | Spoofing | Open Question §2 — currently a known limitation |
| Email-send failure leakage | Information Disclosure | Don't leak email failure as 500 — log + return 200 (Code Examples §2) |
| CSRF via cookie session | Tampering | Existing `auth.SetAuthCookies` includes CSRF cookie + HMAC-bound token; new endpoints set cookies via the same helper |
| Brute-force password guessing | DoS / Spoofing | Account lockout deferred (CONTEXT); rely on bcrypt cost 12 + rate limit on POST /auth/login (Phase 6 will add password login endpoint — NOT in this phase) |
| Brute-force token guessing | Spoofing | 256-bit tokens — at 1M req/s would take ~10^60 years to enumerate |
| Email phishing via reset link | Spoofing | DKIM/SPF/DMARC handled by Resend; subject sanitization already in `EmailService` |

**Note on password login endpoint:** This phase does NOT add `POST /auth/login` for password-based login. CONTEXT spec lists only signup, reset, verify, resend. Phase 6 (frontend) needs a way to log in with password — **this is a research gap that should be flagged.** See Open Question §6 below if upgrading. The existing OTP `/auth/verify-code` flow remains the primary login. **Either:** add `POST /auth/login` to this phase's scope (recommend), **or** Phase 6 ships signup-only and users immediately log in via OTP after signup. Discuss-phase decision.

**Open Question §6 (added during security review):** Is `POST /auth/login` (email + password → session) in scope for Phase 5.1? CONTEXT does not mention it explicitly, but Phase 6's `login-page.tsx` redesign (AUTH-01) implies a password-login form exists. **Recommend including** `POST /auth/login` in Phase 5.1 for symmetry — without it, a user who signed up with password has no way to log back in via password.
