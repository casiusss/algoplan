## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocking] DB migration application path**

- **Found during:** Task 1, after `sqlc generate` succeeded but `TestSendCode` returned 500 "failed to lookup user".
- **Issue:** The shared local PostgreSQL container is the multi-worktree DB and currently sits at `058_project_repos` (the `feat/repos-per-project` branch's migration 058). The worktree branch (`worktree-agent-a11ab91a`) carries a different `058_drop_autopilot_priority_and_project_id`. Running `make migrate-up` would attempt to apply both migrations in sequence and fail because the conflicting 058 cannot be re-recorded.
- **Fix:** Applied migration 059 directly via `psql -f` and inserted its row into `schema_migrations` manually. Migration 059 is schema-additive on the `user` table only (no overlap with the divergent 058 on `autopilot`/`project_repo`), so the application is safe and reversible via the down migration.
- **Files modified:** none (DB-side only). The migration files themselves are committed unchanged.
- **Commit:** N/A (DB-side action). Documented here so the verifier knows that production / a fresh worktree base would apply migration 059 via standard `make migrate-up` once the upstream branch alignment is sorted out.

**2. [Rule 3 — Blocking] sqlc binary version drift**

- **Found during:** Task 1, after `sqlc generate`.
- **Issue:** All `server/pkg/db/generated/*.sql.go` files received a header bump (`sqlc v1.30.0` → `sqlc v1.31.1`) because the locally installed sqlc is newer than the version that produced the prior committed output. Generated bodies are byte-identical otherwise.
- **Fix:** Committed all 24 regenerated files together with `models.go` and `user.sql.go`. The plan rule "Do not hand-edit generated files — only commit the regeneration output" makes this the correct disposition.
- **Commit:** `6fe8ab28` (combined with the other Task 1 changes).

### Observations (no code change required)

- `go mod tidy` removes the bcrypt dep because nothing imports it yet. Re-running `go get golang.org/x/crypto@v0.50.0` keeps it in `go.mod` as `// indirect`. Plan 01 will turn it into a direct dependency the first time `bcrypt.GenerateFromPassword` lands. The validation grep `grep "golang.org/x/crypto v0.50"` matches the indirect line, so the contract holds.
