## Decisions Made

1. **Naming: `dummyBcryptHashForTiming` (handler) vs `dummyBcryptHash` (test).** The Plan 00 RED scaffolds had introduced a package-level test const `dummyBcryptHash` (a static string used to seed insertions in `signupTestUser` and `resetUserWithToken`). The plan instructed me to add a `dummyBcryptHash` package var in the handler for timing equalization — same package, same name, hard collision (`redeclared in this block`). Renamed the production var to `dummyBcryptHashForTiming` because it is the conceptually narrower thing (only used by Login) and `dummyBcryptHash` in the test file is referenced from two existing tests + scaffolds and I did not want to touch Plan 03 territory. Rationale documented inline in code.
2. **Test fixture password hashing at `bcrypt.MinCost`.** `signupTestUser` previously inserted a static `dummyBcryptHash` string that did not correspond to any real password. Plan 01 needed it to bcrypt-validate against the password the test passes in. Used `bcrypt.MinCost` (cost 4) — production cost 12 would have added ~250ms per signupTestUser call across many tests. Cost 4 is acceptable for test fixtures (no production secrets ever live there) and still exercises the genuine bcrypt verify code path.
3. **Atomic commit boundary preserved despite single-edit implementation.** I initially wrote Signup + Login + dummyHash + LoginRequest in one Write call to auth_password.go, hit the test-fixture name collision, fixed it, then deliberately reverted Login back to its 501 stub before committing Signup so each task gets its own atomic commit — bisection and review value. Re-added Login as a second commit.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Renamed handler-side `dummyBcryptHash` to `dummyBcryptHashForTiming` to resolve same-package name collision with test fixture.**
- **Found during:** Task 03 (Login handler)
- **Issue:** Plan 00 had already declared `const dummyBcryptHash = "$2a$12$..."` at package scope in `auth_password_test.go` for use as a static placeholder in `signupTestUser` and `resetUserWithToken` insertions. The plan body for Task 03 instructed me to add `var dummyBcryptHash []byte` in `auth_password.go` (same package). Go forbids same-name declarations in the same package — `redeclared in this block`. Additionally, the test referenced `hash.String == dummyBcryptHash` which would have flipped from `string == string` to `string == []byte` (mismatched types).
- **Fix:** Renamed the production handler variable to `dummyBcryptHashForTiming`. Documented the naming rationale inline so a future reader understands why two similarly-named symbols coexist.
- **Files modified:** `server/internal/handler/auth_password.go`
- **Verification:** `go test ./internal/handler/ -run 'TestSignup_|TestLogin_' -count=1` green; `go vet ./...` clean.
- **Committed in:** `3cb60285` (Task 3 commit, since the symbol is only used by Login)

**2. [Rule 3 - Blocking] Updated `signupTestUser` to bcrypt-hash the supplied password instead of inserting a static placeholder.**
- **Found during:** Task 03 (Login handler)
- **Issue:** Plan 00 scaffold inserted `dummyBcryptHash` (a static string that does not correspond to any real password) as the row's `password_hash`. `TestLogin_Success` calls `signupTestUser(t, email, "atLeast12Chars!")` and then expects `POST /auth/login {email, password: "atLeast12Chars!"}` to return 200 — impossible if the stored hash doesn't decrypt that input. Plan note explicitly anticipated this: *"Plan 01 will swap dummyBcryptHash for a real bcrypt hash of `password` so TestLogin_Success can authenticate against it."*
- **Fix:** `signupTestUser` now calls `bcrypt.GenerateFromPassword([]byte(password), bcrypt.MinCost)` and inserts the resulting hash. Cost 4 (MinCost) keeps test runtime sane while exercising the real bcrypt verify path. Removed the `_ = password // referenced once Plan 01 wires bcrypt-aware variant` placeholder.
- **Files modified:** `server/internal/handler/auth_password_test.go`
- **Verification:** TestLogin_Success green.
- **Committed in:** `3cb60285` (Task 3 commit, since this enables the Login tests)
