## Accomplishments

- Closed the Phase 5.1 SC#2 gap: POST /auth/password-reset/request now produces a fresh reset-token hash + 1h expiry on known emails AND returns the identical 200 body on unknown emails (no DB write, no email send, no dummy bcrypt). 60s per-email cooldown via deterministic `time.Since(expiresAt - 1h)`.

## Decisions Made

- **Cooldown reconstruction over a separate `password_reset_issued_at` column.** Reused Plan 02's deterministic pattern: `issuedAt = password_reset_expires_at - 1h`. No schema change, no clock-skew sensitivity at the cooldown boundary, and the rate-limit value tracks any future change to the issuance window automatically (because both ends use the same constant).
- **Single 401 wording for unknown / expired / reused tokens.** Distinguishing them would help an attacker more than it helps a legitimate user (who would just request a fresh link).
- **No dummy bcrypt on unknown-email reset request.** Per Open Q §4 RESOLVED: parity with OTP `SendCode`, which also doesn't. Future security review can re-open if timing-side-channel hardening is escalated.
- **No JWT invalidation on password reset.** Per Open Q §2 RESOLVED: stateless 30-day JWTs remain valid after a reset (known limitation). The future `password_changed_at` column + JWT middleware check is documented as a follow-up phase concern.
- **Constant `bcryptCost` from Plan 01 instead of literal `12`.** Single tunable point across Signup / Login / PasswordResetConfirm.
