## Blockers (must fix before execution)

### B1 — `TestSignup_Gated` scaffold uses non-functional gating mechanism
**Dimension:** task_completeness / verification_derivation
**Plan:** 00 (Task 5.1-00-03), enforced by Plan 01 (Task 5.1-01-02)

Plan 00 scaffold says:
```
TestSignup_Gated // ALLOW_SIGNUP=false (set via t.Setenv) → 403
```
And Plan 01 line 349 says:
```
Signup gating regression: TestSignup_Gated uses t.Setenv("ALLOW_SIGNUP", "false")
— verify the request returns 403 and no user row is created.
```

**But the gating check reads `h.cfg.AllowSignup`** (`server/internal/handler/auth.go:190`), which is a Config struct field bound at handler construction in `TestMain` (`handler_test.go:58`):
```go
testHandler = New(..., Config{AllowSignup: true})
```
`os.Getenv("ALLOW_SIGNUP")` is NOT read by `checkSignupAllowed`. `t.Setenv` will not flip the gate. The test will assert 403 and fail with 200.

**Fix options (planner choice):**
1. Build a per-test handler instance with `Config{AllowSignup: false}` (mirrors `TestSignupGating` in `auth_signup_test.go:19-66` which does exactly this for `checkSignupAllowed`).
2. Add a `WithConfig(Config) *Handler` test helper that returns a shallow-copied handler with the new cfg, and swap in `testHandler.WithConfig(Config{AllowSignup: false})` for the gated case.
3. Refactor `checkSignupAllowed` to consult an env var (rejected — diverges from existing pattern).

**Recommendation:** Option 1 — mirror the existing test pattern. Update Plan 00 Task 03 scaffold AND Plan 01 Task 02 step 4 ("Pitfalls to verify") to specify constructing a separate handler for the gated test.

### W2 — `dummyBcryptHash` initialization risks data race in `init()`
**Dimension:** task_completeness
**Plan:** 01 (Task 5.1-01-03)

Plan 01 step 2 says: "Add a `package-init` block (or a `var` initializer) that generates it once at startup … Then drop the literal `var dummyBcryptHash = []byte(...)` and declare just `var dummyBcryptHash []byte`."

Better pattern: use `sync.Once` or generate via `var dummyBcryptHash = mustGenerateDummy()` to keep the var read-only post-init. The `init()` approach works but bcrypt cost 12 takes ~250ms — noticeable startup delay. Acceptable trade-off but worth noting.

**Recommendation:** Either accept ~250ms startup hit (document in code comment) or precompute once and embed as a literal constant generated by a `//go:generate` step. Lowest-friction fix is to accept the init-time cost and add a comment.

**Severity:** Warning rather than blocker — the resolutions are materialized in plans even though the marker is missing. Planner can either rename the heading or add inline `RESOLVED:` lines to each question.

### W4 — `TestPasswordResetConfirm_Success` should also assert old password no longer authenticates
**Dimension:** verification_derivation
**Plan:** 03 (Task 5.1-03-03)

The success test asserts the new password hashes correctly and the token is cleared. It would be stronger to also assert that `POST /auth/login` with the OLD password returns 401 after the reset. This catches a class of regression where the password update is partial (e.g., a typo in the SQL only updates the token columns).

**Recommendation:** Add this assertion to `TestPasswordResetConfirm_Success` or add a `TestPasswordResetConfirm_OldPasswordRejected` companion test.

### W5 — Plan 02's resend rate-limit window has off-by-near-zero risk under clock skew
**Dimension:** task_completeness
**Plan:** 02 (Task 5.1-02-03)

The rate-limit gate is:
```go
if user.EmailVerifyExpiresAt.Valid &&
    time.Until(user.EmailVerifyExpiresAt.Time) > 23*time.Hour+59*time.Minute {
    // 429
}
```
This means: "if the existing expiry is more than 23h59m in the future, the previous resend was less than 1m ago". Works — but is sensitive to:
- Clock drift between DB host and app host (Postgres `now()` vs Go `time.Now()`).
- `time.Until` returning a negative for tokens already past expiry — no false positive, just potentially a confusing edge.

Same logic in Plan 03 (`> 59*time.Minute` for the 1h reset-request window) has slightly more headroom (1m of 60 = 1.7%) versus Plan 02 (1m of 1440 = 0.07%) — Plan 02 is more sensitive.

**Recommendation:** Either document the assumption (DB and app clocks agree to within seconds — generally true in single-host dev / managed DB prod) OR replace with a dedicated `last_email_verify_sent_at` column. Acceptable as-is for v1; flag for follow-up.
